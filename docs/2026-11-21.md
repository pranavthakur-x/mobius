# Multi-agent orchestration

From commits `a816a38` and `f568c27` on 21 Nov 2026.

## What it does

One orchestrator sits on the chat. Every message goes to it first.

It either answers, or it hands the request to one role as a task. A question gets a direct answer when the catalog is enough. A code change goes to Software Engineer. A review goes to Code Review, and only when a review was asked for.

The routing result is one JSON object: `think`, `action` (`reply` or `delegate`), `reply`, `team_id`, `role_id`, `task`.

## Separate context

Each role is its own session.

- The orchestrator stores what you typed and its own reply. A delegation reply is the acknowledgement, not the worker's transcript.
- The next routing call does not replay that transcript. It sends the new message and the team list (ids and names).
- Software Engineer does not see Code Review's messages. Code Review does not see Software Engineer's messages.
- A second task to the same role is appended to that role's own history.
- They share the working folder, so one role can read a file another role wrote.

The only text shared across a team is a standing directive (`steer engineering …`). That short note is prepended to the next task. It is not the other agent's conversation.

## Teams and roles

Roles are YAML files in `roles/`. Departments are YAML files in `roles/departments/`.

A new chat starts a team for every department in that folder. Engineering (Software Engineer, Code Review) and Product (Product Manager) both come up. Adding a department file and restarting loads it too.

Each role gets only the tools listed in its file. Code Review can read and search. It cannot edit files or run commands. An unknown tool name fails closed.

## Limits

Every agent, including the orchestrator and each worker, uses `config/agent.toml`: step count, cost, and timeout. That limit is part of the session prompt. One turn cannot run more tool calls than the steps still left.
